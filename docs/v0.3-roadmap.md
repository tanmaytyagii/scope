# SCOPE v0.3 — ecosystem and adoption

v0.2 made SCOPE a complete standalone tool: workflows run, trace and evaluate offline; runs
compare with baselines and fail CI; the dashboard explains failures; everything installs as
`scope-ai` once published. v0.3 asks one question of every change: **does it make SCOPE more
useful next to the AI stack, CI system and infrastructure a team already has?**

## Audit of v0.2 (2026-09-29)

State: `main` at `fc5398e` (0.2.0 prepared, not tagged, not on npm). Locally everything is
green: 295 tests (with PostgreSQL), 34 end-to-end tests, build, package verification.

**Found broken:** CI on `fc5398e` failed (Node 24 test job). A GitHub Action runner test asserted
"passed" on an unchanged workflow, but the starter workflow's warn-level latency gate (p95 +50%
over a millisecond-scale baseline) fired on a loaded runner — a timing-dependent test. Fixed first:
the runner tests remove that gate from their project, since they test the action, not timing.

**What integrates today**

| Path into SCOPE | Status |
| --- | --- |
| `scope run` workflows (YAML) | Complete: OpenAI, Anthropic, any OpenAI-compatible endpoint, offline models |
| `@scope-ai/sdk` (TypeScript) | Manual spans; `span.recordModelCall(...)` for model calls — every call site needs code |
| `POST /api/v1/ingest` | SCOPE's own JSON protocol — any language, but nothing speaks it yet |
| OpenTelemetry | Not supported, although the data model follows it (ADR 0003) |
| CI | GitHub Action; any CI through exit codes, Markdown and JSON reports |

**Gaps that matter for adoption**

1. *Instrumenting an existing application is manual.* No framework, SDK or OpenTelemetry path:
   a team using the OpenAI SDK, the Vercel AI SDK, LangChain or LlamaIndex must hand-write spans.
2. *Redaction has holes.* The SDK does not redact span attributes, event attributes or status
   messages; spans written by `scope run` go straight to the store, so an attribute such as
   `api_key` set in a `function` step is stored as-is. Sensitive keys match exactly, so
   `http.request.header.authorization` or `openai_api_key` are not masked.
3. *CI outside GitHub gets only an exit code and files.* No JUnit report, which GitLab, Jenkins,
   CircleCI and Azure Pipelines render natively.
4. *Regressions do not say what changed in configuration.* Baselines record results, not the
   parameters or workflow version they came from, so "pass rate dropped" never comes with
   "because `sentences` went from 2 to 1".
5. *Data only flows in.* No way to export traces or results, or to turn observed traces into
   dataset cases — the loop from production back to regression tests is manual.
6. *Examples are not tested.* Nothing in CI runs `examples/`; custom evaluators have no example.
7. *Release workflow uses unpinned third-party actions* with `id-token`/`packages: write`
   permissions, and `actions/checkout@v4`/`setup-node@v4` run on the deprecated Node 20 runtime.

## Architecture: where integrations live

No plugin system. Each extension point is a plain interface or a data format, chosen by what
crosses the boundary:

| Concern | Lives in | Extension point |
| --- | --- | --- |
| Domain model, redaction, pricing, comparison | `@scope-ai/core` | — (pure, no dependencies) |
| Recording traces in an application | `@scope-ai/sdk` | `Tracer`, `TraceExporter` |
| Instrumenting a vendor client | `@scope-ai/sdk` (structural wrappers, no vendor dependency) | `instrumentOpenAI`, `instrumentAnthropic` |
| Receiving traces from other ecosystems | `@scope-ai/server` | OTLP/HTTP (`/v1/traces`), SCOPE ingest (`/api/v1/ingest`) |
| Calling models from workflows | `@scope-ai/providers` | `ModelProvider`; OpenAI-compatible endpoints by configuration |
| Judging outputs | `@scope-ai/evaluators` | evaluator modules (`type: ./evaluators/x.mjs`) |
| Getting data out | `@scope-ai/cli` | `scope export`, report formats (Markdown, JSON, JUnit) |
| Storage | `@scope-ai/storage` | SQLite, PostgreSQL (one Kysely implementation) |

OpenTelemetry is the integration layer for frameworks: one well-mapped OTLP endpoint covers the
Vercel AI SDK, OpenLLMetry (Traceloop) and OpenInference instrumentations for LangChain,
LlamaIndex and vendor SDKs, in any language — instead of one shallow adapter per framework.
Details: [integrations.md](./integrations.md), [extensibility.md](./extensibility.md).

## v0.3 scope

In priority order; each lists how it is verified.

1. **Fix CI** — the timing-dependent Action test (done above). *Verified: runner suite.*
2. **Redaction everywhere** — the SDK redacts attribute values, event attributes and status
   messages; sensitive keys match by trailing key segments (`openai_api_key`,
   `http.request.header.authorization`); header-like keys are masked in attributes too. A
   privacy guide states what is stored, what leaves the machine and how to turn capture off.
   *Verified: regression tests for each hole above, SDK and server.*
3. **OpenTelemetry ingestion** — `POST /v1/traces` accepts OTLP/HTTP (JSON and protobuf, gzip),
   maps GenAI semantic conventions (and the OpenInference, OpenLLMetry and Vercel AI SDK
   attributes they diverge on) to SCOPE spans with model, tokens and estimated cost, and keeps
   traces whose spans arrive in several requests correct. *Verified: the official OpenTelemetry
   JS exporters (JSON and protobuf) and the Vercel AI SDK's telemetry against a running server;
   mapping unit tests for each convention.*
4. **Client instrumentation** — `instrumentOpenAI(client)` and `instrumentAnthropic(client)`
   record every call (including streams) as a model span, inside the current trace or as its own
   trace; OpenAI-compatible endpoints (Ollama, vLLM, OpenRouter, Gemini's OpenAI endpoint) work
   through the OpenAI client. *Verified: the real `openai` and `@anthropic-ai/sdk` packages
   against local HTTP servers.*
5. **CI beyond GitHub** — `--junit-file` on `scope run` and `scope report --format junit`;
   GitLab CI and generic CI documentation. *Verified: JUnit output parsed in tests.*
6. **What changed, including configuration** — baselines record the parameters and workflow
   version they came from (additive fields); comparisons, reports, the run page and the PR comment
   show parameter differences next to metric and case changes. *Verified: CLI, report and API
   tests.*
7. **Data out** — `scope export` writes traces as JSONL, run results as CSV or JSONL, and traces
   as dataset cases. *Verified: CLI tests round-tripping an export into `scope run --dataset`.*
8. **Evaluator contract** — the custom evaluator contract written down (inputs, result, failure
   behavior, versioning) with a tested example. *Verified: the example runs in CI.*
9. **Examples that run** — every example is executed by the test suite. *Verified: CI.*
10. **Release hardening** — third-party actions pinned to commit SHAs, Dependabot for actions and
    npm, Node 24-based action versions. *Verified: actionlint, a dry-run release.*
11. **Measure, review, document** — OTLP ingestion benchmarked, security review of every new
    input path, guides reorganized around the developer journey.

## Deferred, and why

| Item | Why not in v0.3 |
| --- | --- |
| Python SDK | OTLP ingestion lets Python applications send traces today through standard OpenTelemetry instrumentations; a native SDK waits for a concrete gap |
| LangChain / LlamaIndex adapters of our own | Their OpenTelemetry instrumentations (OpenLLMetry, OpenInference) already exist and map onto SCOPE; a second adapter would be shallower and need its own maintenance |
| Gemini native provider for workflows | Gemini is reachable through its OpenAI-compatible endpoint (configuration only); a native provider adds little until a feature needs its native API |
| Webhook / generic HTTP exporter | No consumer has asked; `scope export` and the HTTP API cover pulling data |
| Exporting SCOPE traces as OTLP | Would duplicate the OpenTelemetry SDK; applications that want both send OTLP to both |
| Plugin system | Every extension point above is a module path or a data format; nothing needs discovery or lifecycle hooks |
| Unified server-side search | The command palette jumps to runs and trace ids and hands text to trace search; search across entities waits for data sets where that is not enough |
| Datasets page | Datasets are files reviewed like code; a page would show what `scope validate` and the repository already do |
| Retention (`scope prune`), rate limiting | Still no storage pressure measured; OTLP ingestion may change that, and the benchmark will show it |

## Compatibility

Everything in v0.2 keeps working. New behavior is additive: a new endpoint (`/v1/traces`), new
SDK functions, new CLI flags and a new command, new optional fields in baseline files (ignored by
v0.2, which reads baselines with non-strict schemas), and new optional fields in API responses.
One behavior change is deliberate and called out in the CHANGELOG: more values are redacted
(attribute values in the SDK, keys ending in a sensitive name).
