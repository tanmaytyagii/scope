# SCOPE v0.2 roadmap

v0.1 is feature-complete: workflows, tracing, evaluators, gates, baselines, the CLI, the HTTP
API, the dashboard, the GitHub Action, Docker, guides and examples all exist and are tested. v0.2
is about turning that into something an external developer can **install, trust and adopt**
without the author. This plan comes from an audit of the repository and of CI on GitHub
(2026-09-29); it lists what will change and why, and what is deliberately deferred.

## Audit

**State.** Lint, typecheck (packages, dashboard, E2E specs), 248 unit/integration/CLI tests, the
PostgreSQL storage suite, 9 Playwright tests with axe scans, the build and the package smoke test
all pass locally. On GitHub, all seven CI jobs pass on `main`.

**Strengths.** A clear package graph (`core` pure, only `storage` knows SQL, only `server` knows
HTTP); a typed API contract with a generated OpenAPI document and a contract test; honest
evaluator taxonomy; privacy applied twice; real-data tests (engine-seeded, CLI-seeded E2E);
documentation examples checked against the running product.

**Weaknesses found.**

| Area | Finding |
| --- | --- |
| Reliability | The GitHub Action self-test workflow never ran: `.github/workflows/action.yml` is invalid YAML (an unquoted `: ` in a `run:` value). Nothing lints workflow files. |
| Reliability | The action's runner (`run.mjs`) is only exercised by that broken workflow; no local test covers it. |
| Reliability | Server/API tests run on SQLite only; PostgreSQL is covered at the storage layer but not through the API mapping. |
| Distribution | Nothing is on npm. Installing means cloning and building; the GitHub Action rebuilds SCOPE from source on every run (~30 s); there is no release process, version tooling or published Docker image. |
| First run | `scope run` requires a workflow path even in a project that lists its workflows, so the natural `scope init → scope run → scope ui` sequence does not work as typed. |
| CLI | `scope validate` does not check datasets (a malformed case is found only at run time). `scope doctor` does not check credentials against the provider, baselines, datasets or whether `.scope/` is ignored by git; `architecture.md` mentions `doctor --network`, which does not exist. `scope init` prints `./../../..` paths for directories outside the working directory. |
| Debugging | The trace explorer shows one trace; stepping through a run's failing cases means going back to the run each time. Large traces have no way to narrow the span tree (errors only, model calls only, by name). |
| Evaluation | A run page shows gate results but not *what changed* against its baseline (which cases regressed); that needs a separate trip to Compare. |
| Experiments | Compare handles two runs; `scope run --all-variants` produces N runs that can only be compared pairwise in the dashboard. |
| GitHub | The Action writes a job summary and annotations, but the result is not visible on the pull request itself. |

**Technical debt.** API-key auth has no cache (fine at current scale). Overview buckets are UTC
aligned. The dashboard bundle is ~160 KB gzipped.

## v0.2 scope — outcome

In priority order, each with what shipped and how it is verified. All ten are done.

1. **Reliability of CI and the Action** — done. The Action's self-test workflow was invalid YAML
   and never ran; fixed, and every workflow is linted with `actionlint` in CI. The runner has its
   own Vitest suite, which found that `fail-on-gates: false` reported `passed` for failed gates
   (fixed). The API contract tests also run on PostgreSQL, which found that installs using a
   dedicated schema could not migrate (fixed).
2. **Distribution** — done, not yet published. `npm run release:version -- x.y.z` sets one
   version everywhere; every package has npm metadata, a README and the license (tarballs no longer
   ship `.tsbuildinfo`); `scope-ai` installs the `scope` command; a `v*` tag runs
   `.github/workflows/release.yml` (verify → npm with provenance and GHCR multi-arch image → GitHub
   release from the CHANGELOG; a manual run is a dry run); the Action installs from npm when its
   version is published. Verified by `verify-packages --packed`, the install smoke test (which
   installs `scope-ai` and `@scope-ai/sdk` the way users will), `publish.mjs --dry-run` and
   actionlint. [RELEASING.md](../RELEASING.md) lists the one-time npm setup only the maintainer
   can do.
3. **First five minutes** — done. `scope run` without a path runs every workflow (all checked
   before any runs); `scope init` prints `scope run` and `scope ui --open`, with absolute paths
   outside the current directory. Install docs say plainly that npm comes with the first release.
4. **CLI diagnostics** — done. `scope validate` checks datasets (code frames, "did you mean" for
   misspelled inputs); `scope doctor` checks datasets, baselines (missing, stale, unused) and
   whether git ignores the local database; `scope doctor --network` asks each provider in use for
   its model list (read-only, no tokens).
5. **Trace debugging** — done. "Failing case 2 of 5" with `[`/`]` in the trace explorer (served
   by `failingCases` on the trace API), and a span filter by text, errors or model calls.
6. **What changed** — done. The CLI stores the comparison its regression gates used
   (`run_comparisons`, migration 0002), because the baseline file may come from another machine;
   the run page shows it, linking this run's traces (and the baseline's, when that run is in the
   same database). `scope report` uses it too, so replacing a baseline later no longer rewrites
   old reports.
7. **Experiments** — done. Up to four runs side by side (`/compare?runs=`, `scope compare a b c
   d`): the parameters that differ, each metric per run with the best marked (ties within noise
   share it), and the cases whose outcome differs.
8. **Pull-request comments** — done. `comment: true` posts one comment and updates it in place;
   missing permission is a warning; tested against a fake GitHub API.
9. **Performance check** — done. `npm run bench` and [performance.md](./performance.md): up to
   100,000 traces and 1,000-span traces, nothing that needed changing.
10. **Docs and release** — done. README and guides updated with regenerated screenshots
    (`scripts/screenshots.mjs`), CONTRIBUTING lists real good first contributions, status docs
    current; 0.2.0 is prepared in the CHANGELOG and tagged only by the maintainer.

## Deferred, and why

| Item | Why not in v0.2 |
| --- | --- |
| Python SDK | Large, and best done once the ingestion protocol has external users; the protocol is documented for anyone who needs it now |
| OTLP ingestion | Needs an OTLP/HTTP protobuf decoder and a mapping spec; the data model is ready (ADR 0003) |
| Auto-instrumentation of vendor SDKs | Wrappers must track vendor SDK changes; better after npm publishing so they can be versioned independently |
| Accounts, SSO, RBAC | Project-scoped API keys are the v0.x authorization model |
| Dataset management UI | Datasets stay files in the repository, reviewed like code |
| Retention (`scope prune`) | No user has hit storage limits yet; the database is inspectable and deletable |

## Compatibility

Every v0.1 workflow, dataset, baseline, command and API endpoint keeps working; new behavior is
additive (`scope run` without a path was a usage error before; `scope compare` still takes two
runs; new API fields and endpoints only). The database gains one table (`run_comparisons`,
migration `0002_run_comparisons`), applied automatically on first use; a database upgraded by
0.2 cannot be opened by 0.1 with auto-migration on. Runs made by 0.1 have no stored baseline
comparison, and the run page does not show one for them. Package names do not change; `scope-ai`
is an additional package.
