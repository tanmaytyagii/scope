# SCOPE v0.4 — production adoption

v0.3 connected SCOPE to the stacks teams already use: OpenTelemetry, the OpenAI and Anthropic
SDKs, CI systems beyond GitHub. v0.4 asks a harder question of every part: **would an external
developer trust this in a real AI application?** That means no silent data loss, bounded
resource use under real payloads, a database that does not grow forever, a deployment an operator
can run, and results that say exactly what produced them.

## Audit of v0.3 (2026-09-29)

State: `main` at `5d850bc`, tagged `v0.3.0` and pushed. Locally everything is green: `npm ci`
(0 vulnerabilities), lint, typecheck, 366 tests with PostgreSQL, build, 12 packages verified, 34
end-to-end tests.

**On GitHub**

- CI on `main` passes, including the Node.js 24 action versions adopted in v0.3.
- Every Dependabot pull request fails one check, *Dependency audit*: "Dependency review is not
  supported on this repository. Please ensure that Dependency graph is enabled." A repository
  setting only the maintainer can change; the check has never run before because v0.3 had no
  pull requests.
- The v0.3.0 release workflow: verification passed, **npm publishing failed** (the log needs
  repository access; the one-time npm setup in [RELEASING.md](../RELEASING.md) is the likely
  cause), so the GitHub release was not created either. SCOPE is still not installable from npm.
- The release commit also added `my-demo/`, a project made with `scope init`, to the repository.

**Measured problems** (reproduced before planning; each item below links to its fix)

| Problem | Measurement |
| --- | --- |
| The SDK loses unrelated traces when a batch is large | 50 traces with ~120 KB of content each: one 6 MB request, rejected with 413 (limit 5 MiB), and all 50 dropped — `exportedTraces: 0, droppedTraces: 50` |
| A large trace is one huge response | A 1,000-span trace with ~120 KB per span: `GET /api/v1/traces/{id}` returns 118.7 MiB of JSON; the server process reaches 1.1 GiB; the dashboard would render all of it |
| The database only grows | No retention or deletion of any kind, in the CLI or the server |
| Nothing guards performance | The whole-project span scan fixed in v0.3 was found by hand; nothing in CI would notice it coming back |

**Gaps found by reading**

- *Reproducibility.* Runs record the workflow version, dataset hash, parameters, variant and git
  state, but not the SCOPE version, the models actually called, or the identity of custom
  evaluator modules — the custom evaluator guide tells users to rename evaluators to compensate.
- *Pricing.* Every price is dated and sourced, but the OpenAI prices date from 2025-08-07, more
  than a year ago, and nothing says so where costs are shown.
- *Self-hosting.* The only compose file is the demo (`scope ui` without authentication). With
  `SCOPE_AUTO_MIGRATE=false` there is no command that applies migrations; backups are one line.
- *Project isolation* is tested for one route, not for the API as a whole.
- *Integrations.* OpenLLMetry and OpenInference mappings (and so LangChain and LlamaIndex) are
  tested only against their documented attributes; cancelled and concurrent instrumented calls
  are untested.

## Scope

In priority order; each lists how it is verified.

1. **No silent data loss in the SDK** — batches bounded by bytes as well as traces; a rejected
   batch (413, 400) is split so one bad or oversized trace cannot take others with it; oversized
   traces are dropped individually and counted. *Verified: exporter tests against a real server
   with a small body limit; the probe above.*
2. **Instrumentation robustness** — cancelled streams, timeouts, retries, concurrent calls,
   huge responses and network failures, each tested with the real SDKs; anything found fixed.
   *Verified: tests.*
3. **Large traces** — the trace detail API can bound the content it returns (spans over the
   budget are marked, not silently emptied) and serves single spans in full; the explorer uses
   both, so a trace of any allowed size loads. *Verified: API tests; the probe; end-to-end test
   with a large trace.*
4. **Retention** — `scope prune` deletes traces and runs by age, project, run or trace, shows
   what it would delete first, and deletes only with `--yes`; `scope server` can prune on a
   schedule when an operator configures it. *Verified: storage, CLI and server tests on SQLite
   and PostgreSQL.*
5. **Performance protection** — query-plan tests for the hot queries, and a CI benchmark that
   compares throughput at two database sizes on the same machine (stable on shared runners),
   so a scan that grows with the database fails CI. *Verified: the checks fail with the v0.3
   bug reintroduced.*
6. **Measured scale** — the benchmark extended to PostgreSQL, memory, database size and
   concurrent ingestion; runs at 100K, 500K and 1M traces; documented deployment boundaries.
   *Verified: the numbers in performance.md, reproducible with `npm run bench`.*
7. **Project isolation** — every route in the route table checked against a second project's
   data. *Verified: an isolation test driven by the route table.*
8. **Self-hosting and operations** — a production-style compose file (`scope server`,
   PostgreSQL, secrets from the environment, health checks, restart policies, a reverse proxy
   example); `scope db status`, `scope db migrate`; backup and upgrade guidance for SQLite and
   PostgreSQL. *Verified: the compose deployment brought up, used through API keys, restarted
   and upgraded.*
9. **Reproducibility** — each run records what produced it: SCOPE and Node.js versions, models
   called, evaluator identities (custom module hashes, judge models), alongside the workflow,
   dataset, parameters and git state it already has; comparisons say when evaluators or the
   SCOPE version changed. *Verified: CLI, API and dashboard tests.*
10. **Integration quality** — the OpenInference and OpenLLMetry mappings tested with their real
    instrumentation packages, including LangChain; documented limitations updated from the
    results. *Verified: tests with the real packages.*
11. **Honest costs** — stale prices flagged wherever a cost uses them; reported usage and
    estimated cost kept distinct in the docs and API. *Verified: tests.*
12. **Public interfaces** — a stability and deprecation policy for the API, SDK, CLI and file
    formats; a CLI consistency pass (help, `--json`, exit codes). *Verified: a test over every
    command's help and JSON output.*
13. **Documentation and examples** — guides grouped as the prompt lists (getting started through
    contributing); an operations guide; a structured-output example; contributor guides per area;
    every example and documented command run. *Verified: examples tests, link check.*
14. **Subtraction** — remove what does not earn its place. *Verified: the final review.*

## Outcome (2026-09-30)

Each item, what it delivered, and what verifies it. Measurements are from the machine in
[performance.md](./performance.md) unless stated.

1. **No silent data loss in the SDK — done.** Requests are bounded by bytes (4 MiB) and traces;
   the queue by bytes (32 MiB). A 413, or a 400 naming records, splits the batch until only the
   refused traces are left, and those are counted as dropped. `sdk-export.test.ts` sends 20
   normal traces, one larger than the server's limit and one naming an unknown run to a server
   that accepts 256 KiB: the 20 are stored, 2 dropped. Before, the audit's 50 traces were all
   dropped.
2. **Instrumentation robustness — done.** `instrument-robustness.test.ts` drives the real OpenAI
   and Anthropic SDKs against a local server: streams returned from a traced function and read
   later, cancelled, abandoned, failing midway or malformed; timeouts, retries, network failures,
   malformed responses, concurrent calls, a huge response. What it found is fixed: a stream
   handed to a web framework lost its model span; an unread stream held its trace forever;
   timeouts were recorded as `Error`; empty streamed tool calls were recorded.
3. **Large traces — done.** The audit's 1,000-span, 118.7 MiB trace is a 2.3 MiB response with
   the explorer's 2 MiB budget; the selected span loads on demand. Verified by API tests and an
   end-to-end test with a large trace.
4. **Retention — done.** `scope prune` and `SCOPE_RETENTION`, tested on SQLite and PostgreSQL in
   storage, CLI and server tests. Its cost at scale is in [performance.md](./performance.md).
5. **Performance protection — done.** `query-plans.test.ts` fails with the v0.3 bug put back and
   found a second instance (a run's case list); `npm run bench:check` runs in CI and gives a
   ratio of 6.5 with the v0.3 bug, about 1 without (limit 4).
6. **Measured scale — done.** `npm run bench` now measures PostgreSQL, concurrent OTLP, a
   bounded trace read, retention, size and memory. Run at 100,000, 500,000 and 1,000,000 traces
   on SQLite and 100,000 and 500,000 on PostgreSQL (the machine lacked the disk for 1,000,000);
   results, environment and boundaries in [performance.md](./performance.md). Lists, filters and
   trace details stay under 1 ms on SQLite at a million traces. The runs found three things that
   grow faster than the data, each analyzed on a separate 500,000-trace database: dashboard
   aggregates over a window holding a million traces take 3–4 s on SQLite, which is reading
   indexes that no longer fit in memory rather than computing (a known limitation, with rollups
   on the roadmap); a first retention pass on a large database takes seconds, with one random
   read per deleted span; and the 0004 covering indexes make deleting 2–3× slower (a controlled
   A/B test on one database), a cost kept for their read speed. Reviewing the plans at 500,000
   traces found one real problem, fixed: on PostgreSQL, retention's plan read every trace, span
   and evaluation in the database (0.5–3 s at 500,000 traces, now 5–8 ms for an hourly-sized
   pass); the query-plan test now checks PostgreSQL too. Every other hot path stays on its
   indexes on both databases, and SQLite's plans are the same at every size.
7. **Project isolation — done.** `isolation.test.ts` asks every route in the route table for a
   second project's data with the first project's key (404 everywhere, the other project's data
   in no response) and tries to write into it (refused).
8. **Self-hosting and operations — done.** `deploy/compose.yaml`, `scope db status | migrate |
   backup`, the [operations guide](./guides/operations.md). Brought up by hand as a new operator
   would (keys, OTLP ingestion, reading back with a read key, restart, the HTTPS profile, an
   upgrade of a v0.3.0 deployment with its data), and in CI on every push and pull request. Running it found two
   logging problems, fixed: a refused request did not name its key, and passing health checks
   filled the log.
9. **Reproducibility — done.** Run manifests (migration 0003) and comparisons that name changed
   files and SCOPE versions, in the CLI, reports, pull request comments and the dashboard.
10. **Integration quality — done.** OpenInference and OpenLLMetry run in CI with their real
    packages for the OpenAI SDK and LangChain. They found three mapping errors (workflow roots,
    OpenLLMetry content, OpenInference's model name), fixed in the OTLP mapping, and two
    behaviors SCOPE cannot fix — no token counts for their streamed calls, no span for a failed
    call — which the tests pin down and the [trace contract](./instrumentation-contract.md)
    documents.
11. **Honest costs — done.** Prices older than 180 days are marked in the dashboard and by
    `scope doctor`. The OpenAI prices were checked against OpenAI's pricing page on 2026-09-30
    (unchanged) and re-dated; the Anthropic prices date from 2026-06-24.
12. **Public interfaces — done.** A stability and deprecation policy
    ([API guide](./guides/api.md#stability-and-deprecation)); `cli.test.ts` checks every
    command's help and that `--json` prints one JSON document; the
    [CLI guide](./guides/cli.md) states the `--json` contract.
13. **Documentation and examples — done.** Guides grouped from getting started to contributing,
    the operations guide, the trace contract. `scope import` was not built: no request for it,
    and traces arrive through the SDK and OTLP already; `scope export` remains the way out.
14. **Subtraction — done.** Two unused dependencies of the CLI and dead dashboard code removed
    (found with knip).

Found along the way and fixed: an older SCOPE with `SCOPE_AUTO_MIGRATE=false` would have used a
database a newer one had migrated; SCOPE now refuses such a database on open, whatever the
setting (tested on SQLite and PostgreSQL).

### Security review

Reviewed for v0.4 (a review by the maintainer's tools and reading, not a formal audit):

- **SQL:** every value is a bound parameter; the only dynamic identifiers come from constants or
  the operator's own configuration. Prefix lookups (`resolveTraceId`, `getRun`) validate their
  input as hex or base32 before building a `LIKE` pattern.
- **Authentication:** API keys carry about 190 random bits, are stored as SHA-256 hashes, looked
  up by hash and compared in constant time; revoked keys are refused; every request names its key
  id in the log, never the key. Project isolation is tested on every route.
- **Inputs:** the only writing routes (`/api/v1/ingest`, `/v1/traces`) require an `ingest` key and
  have a body limit; OTLP strings, stacks, provider and model names are bounded; content is
  redacted again on ingest.
- **Browser:** a strict Content-Security-Policy (`'self'` only, no inline scripts, no framing),
  `no-referrer`, same-origin resource policy; no raw HTML rendering in the dashboard;
  DNS-rebinding protection for `scope ui`. Markdown reports escape case ids and reasons.
- **Deployment:** the image runs as `node`, not root, from a base pinned by digest; the compose
  file publishes the server on loopback only and takes secrets from `.env`; the Caddyfile keeps
  `/metrics` (unauthenticated) off the public address.
- **Known limitations,** recorded in [SECURITY.md](../SECURITY.md): no rate limiting,
  unauthenticated `/metrics`, pattern-based redaction, no user accounts.

### Final review

- **A developer adopting SCOPE** can run a workflow offline in minutes, instrument an OpenAI or
  Anthropic client in one line, or point OpenTelemetry (OpenInference, OpenLLMetry, the Vercel AI
  SDK) at it, with every path tested against the real packages and the differences written down.
  The largest obstacle is outside the code: SCOPE is still installed from source until a release
  reaches npm.
- **An operator** gets a compose deployment with HTTPS, health checks, key rotation, retention,
  backups, forward-only migrations that refuse a newer database, and measured boundaries. What
  they must add themselves: rate limiting at the proxy, monitoring of disk and `/readyz`, and
  PostgreSQL or short windows for dashboards over around a million traces.
- **A maintainer** has CI that fails on lint, types, tests on both databases, query plans on both
  databases, a size-independence check, end-to-end and accessibility tests, the packed install,
  the image and the compose deployment. Only the maintainer can finish the release (npm setup,
  the dependency graph setting for the *Dependency audit* check) and decide whether `my-demo/`,
  added by the v0.3.0 release commit, belongs in the repository.

## Deferred, and why

| Item | Why not in v0.4 |
| --- | --- |
| Webhooks and notifications (Slack, …) | No event source that CI does not already report: runs happen in CI (job status, annotations, PR comments) or on a developer's machine, and the server stores traces but does not evaluate them. Notifications become useful with online evaluation (roadmap), which would produce events nobody else sees |
| User accounts, SSO | API keys scoped to one project cover shared servers today; accounts are a large surface (sessions, passwords or SSO, roles) with no request for them yet |
| A model catalog (context windows, capabilities) | No feature uses them; the pricing table (dated and sourced, overridable in `scope.yaml`) is the only model data SCOPE needs, and a large hand-maintained catalog would go stale |
| `scope import` | Decided with the user journey (item 13); the outcome section records the decision |
| Externalized payload storage (object stores) | Payloads are bounded per field (64 KiB by default) and now per response; external storage adds an operational dependency for a limit most users can raise |
| Python SDK | Python applications send traces through OpenTelemetry today; unchanged from v0.3 |

## Compatibility

New behavior is additive: a new query parameter and endpoint on the trace API, new CLI commands
(`prune`, `db`), new optional fields on runs, spans and configuration diffs, and two migrations:
0003 adds a nullable column, 0004 adds covering indexes (and replaces `traces_project_start_idx`
with one that starts with the same columns). A database migrated by v0.4 cannot be opened by
v0.3 with auto-migration (verified with the 0.3.0 image), and v0.4 refuses any database a newer
SCOPE has migrated; the [operations guide](./guides/operations.md#migrations-and-upgrades) says
how to back up before upgrading.

One behavior changed on purpose: the SDK exports a trace whose function returned with spans
still open (a stream handed to a web framework) when those spans end, up to `openSpanGraceMs`
(10 minutes) later, instead of at once with those spans closed as errors. `scope run` is
unchanged.
