# Performance

Measured, not estimated. `npm run bench -- --traces N` reproduces the server numbers on any
machine (`--database postgres://…` for PostgreSQL); the dashboard numbers come from Playwright
against `scope ui` with the same data. CI runs `npm run bench:check`, which compares timings at
2,000 and 50,000 traces on the same runner and fails when an operation slows down with the size
of the database.

## How it was measured (2026-09-30)

- **Machine:** Apple M4 (10 cores), 16 GiB, internal SSD, macOS 26.2. It was in normal use during
  the runs — Docker Desktop's VM (7.65 GiB) and a browser were running, and memory was short
  (130 MB free at one check) — so timings that depend on what is cached vary a lot between runs:
  the overview at 500,000 traces took 0.3 s in the benchmark and 3–6 s in a later run on another
  database of the same size. Read them as orders of magnitude on this class of machine.
- **Software:** Node.js 24.12.0; SQLite 3.50.4 (`node:sqlite`, WAL, `synchronous = NORMAL`,
  64 MiB page cache); PostgreSQL 17.11 (`postgres:17-alpine`, default settings: 128 MB
  `shared_buffers`, 4 MB `work_mem`) in Docker Desktop 29.3.1's VM (10 CPUs, 7.65 GiB), reached
  over TCP from the host.
- **Data:** generated by the real tracer: traces of 6 spans (a root, 4 steps, a model call on
  `gpt-5` or `gpt-5-mini` with token counts) and one heuristic evaluation each, stored in batches
  of 500. Every trace is generated during the run, so all of them fall in the 30-day window the
  aggregate queries use: the worst case for those queries. Then one 1,000-span trace (the
  default per-trace limit), OTLP requests, and 5% more traces dated 90 days ago, which the
  retention step deletes.
- **What a timing covers:** API timings are the median of 5 requests through the server
  in-process (routing, validation, storage, JSON; no network, no browser). Ingestion timings
  include generating the traces with the tracer in the same process.

## What the numbers say

**Lists, filters and trace details do not depend on the size of the database.** They are
keyset-paginated and read indexes by project and time, trace id or run id; on SQLite they take
under a millisecond at a million traces. `query-plans.test.ts` fails if one of them starts
walking a whole table or project. On PostgreSQL they took 2–10 ms at both sizes, slower than
SQLite because every statement is a round trip into the VM.

**Dashboard aggregates grow with the traces in their window,** not with the database: the
overview, models and evaluator pages read a covering index over the window (migration 0004) and
count, sum or group what they find. With every trace in the window, that is 90 ms at 100,000
traces and 300 ms at 500,000 — and 3–4 s at 1,000,000 on SQLite. The jump at a million is
reading from disk, not computing: measured again on a 500,000-trace database, the model query's
own work took 0.36 s, but its first run took 5.6 s reading index pages, and the overview, which
reads three indexes that together exceed the 64 MiB page cache, took 3–6 s on every run on this
memory-starved machine (0.3 s once they fit, with a 256 MiB cache). So on SQLite, the
aggregates stay fast while the indexes for the window fit in memory: the page cache plus what the
operating system keeps. The dashboard opens on a 7-day window.

**Two reads walk the whole project by design:** sorting every trace by duration
(`sort=slowest`, 200 ms at a million) and searching for a term in only a few traces (387 ms),
which scans traces until it has a page of matches. A common term returns at once.

**Ingestion slows as the database grows,** from 1,249 to 534 traces a second on SQLite and from
2,129 to 604 on PostgreSQL, as trace-id indexes outgrow memory and each insert touches pages
that are no longer cached. There is no scan: plans are the same at every size (SQLite picks
plans without statistics; checked on 2,000- and 500,000-trace databases). OTLP requests on
SQLite took 20–40 ms each at 500,000 traces, with 100–300 ms pauses when the WAL is written
back; sequential and concurrent senders reach the same rate once measured side by side (1,200–
1,900 traces/s at 500,000). On PostgreSQL, an OTLP request of 100 traces makes 108 statements —
one update per trace to recompute its totals — and each is a round trip: that is why OTLP on
PostgreSQL is slower than on SQLite here, and it would be the first thing to batch if a
deployment needs more than a few hundred traces a second from one sender.

**Retention costs about one random read per deleted span and evaluation.** Deleting finds each
trace's spans and evaluations through their trace-id indexes, whose pages for old traces are
scattered, so time grows with how much is deleted and how much of the database is cached: 50,000
traces took 85 s at a million. Planning reads the same pages, so a first `scope prune` on a large
database takes seconds (6–15 s here), and a repeat is faster once they are cached. A server with
`SCOPE_RETENTION` deletes an hour's worth each hour.

On PostgreSQL, planning used to cost more: its selection of traces
(`run_id in (…) or id in (…)`) could not use an index there, so every plan read every trace,
span and evaluation in the database — 0.5–3 s at 500,000 traces however little was selected,
and more as the database grew. It is now a union with each side on its index: at 500,000
traces, 5–8 ms to plan a 1,000-trace pass and 0.13–0.44 s for 25,000. The query-plan test checks
PostgreSQL's plans too.

The dashboard's covering indexes (migration 0004) make deleting slower: on one 500,000-trace
SQLite database, deleting 12,500 traces took 4.9–12.2 s with them and 1.7–4.4 s without (three
runs each), while planning varied as much within each case as between them (57 ms to 10 s,
depending on the cache). They are kept, because they make the dashboard's aggregates tens of
times faster.

## Boundaries

What was measured, on the machine above:

- **SQLite, up to 1,000,000 traces (6 million spans, 3.9 GiB):** every list, filter, search for a
  common term and trace detail in under 10 ms; ingestion from 1,250 down to 530 traces a second;
  dashboard aggregates over a window holding all 1,000,000 traces in 0.7–4 s.
- **PostgreSQL, up to 500,000 traces (2.3 GiB), default settings:** lists and details in 3–30 ms
  (about 1 ms each once cached, measured again with `EXPLAIN ANALYZE`: every list stops at its
  page); aggregates over 500,000 traces in 0.16–0.42 s; ingestion 600 traces a second.

What follows from it, without having been measured separately:

- Aggregates cost what the traces *in the window* cost: a deployment adding 1,000,000 traces a
  month sees about 230,000 in the default 7-day window.
- Retention bounds all of it: `SCOPE_RETENTION=30d` keeps the database at about 30 days of
  traffic.

Known limitations:

- On SQLite, a dashboard window holding around a million traces takes seconds to aggregate when
  its indexes do not fit in memory, and the first view after a restart has to read them in.
  Shorter windows and retention keep the window small; PostgreSQL aggregated 500,000 traces in
  0.2–0.4 s (not measured beyond that).
- The first `scope prune` on a large database takes seconds to say what it would delete.

Future work, when a deployment needs it (see the [roadmap](./roadmap.md)): pre-aggregated
rollups for the dashboard's time-window queries, which would make them independent of the
number of traces in the window; batching OTLP's per-trace updates on PostgreSQL.

## History

The OTLP benchmark found a real problem in v0.3: span queries that combined a `project_id`
condition with a list of trace ids made SQLite choose a project index and scan every span of the
project, and OTLP ingestion fell to 667 traces/s at 100,000 traces, getting slower as the
database grew. Those queries now select spans by trace id alone, and the query-plan test and
`bench:check` fail if that shape returns. In v0.4 the aggregates' covering indexes took the
models page at 500,000 traces from 5 s to 0.3 s.

## Dashboard

The trace explorer with a 1,000-span trace (100 nested iterations of 8 tool calls and a model
call), Chromium via Playwright, 1440×900:

| Measurement | As is | CPU throttled 4× |
| --- | ---: | ---: |
| Load and render the span tree (1,000 rows, ~11,400 DOM elements) | 80–300 ms | 320–500 ms |
| Arrow key: keydown to the next painted frame | ~17 ms | ~24 ms (one frame + ~8 ms of work) |
| Filter the tree (model calls, errors) | ~80 ms | ~200 ms |

The tree renders every row (no virtualization). At the 1,000-span limit that stays within a
frame per key press even on a throttled CPU, so virtualization — which complicates keyboard
navigation and find-in-page — is not worth it yet. It becomes worth it if the span limit is
raised.

A trace with large payloads (1,000 spans of ~120 KB) is read with a 2 MiB content budget: a
2.3 MiB response instead of 118.7 MiB, and a span's content loads when it is selected.
